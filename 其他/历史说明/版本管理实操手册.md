# 一人公司代码版本管理实操手册

> 适用于：刚学写代码、项目已上线、需要持续小迭代的一人开发者

---

## 一、核心原则（记住这 5 条就够了）

| 原则 | 说明 |
|------|------|
| **main 永远稳定** | main 分支随时可上线，绝不在上面直接改代码 |
| **改动走分支** | 每次改动从 main 切一个 feature 分支，改完合回去 |
| **只提交源码** | node_modules、.jar、.dll、构建产物等不进 Git |
| **提交信息有意义** | `fix: 修复xxx` / `feat: 新增xxx`，不要写"改了点东西" |
| **发布打 Tag** | 每次上线打版本号 Tag（v1.2.8），随时可回退 |

## 三、常用 Git 命令速查表

### 日常操作

```bash
# 查看当前状态（最常用，随时看）
git status

# 查看改了什么
git diff

# 提交所有改动
git add .
git commit -m "fix: 修复登录白屏问题"

# 推送到远程
git push

# 拉取远程最新
git pull
```

### 分支操作

```bash
# 从 main 切出新分支
git checkout main
git checkout -b feature/修复登录bug

# 查看所有分支
git branch

# 切回 main
git checkout main

# 把 feature 分支合并到 main
git merge feature/修复登录bug

# 删掉用完的分支
git branch -d feature/修复登录bug
```

### 版本标签

```bash
# 打版本标签
git tag v1.2.8

# 推送标签到远程
git push origin v1.2.8

# 查看所有标签
git tag

# 查看某个版本的改动
git log v1.2.7..v1.2.8 --oneline
```

## 四、出事了怎么办（应急手册）

### 场景 1：改错了，想撤销还没提交的改动

```bash
# 撤销某个文件的改动
git checkout -- 文件名

# 撤销所有改动
git checkout -- .
```

### 场景 2：已经提交了，想撤销最后一次提交

```bash
# 撤销最后一次提交，但保留改动
git reset --soft HEAD~1

# 撤销最后一次提交，连改动一起丢弃（慎用）
git reset --hard HEAD~1
```

### 场景 3：线上版本出 bug，需要紧急回退到上个版本

```bash
# 查看历史提交
git log --oneline

# 回退到某个版本（不影响远程历史）
git revert 有问题的提交ID

# 或者直接回退到某个 Tag
git checkout v1.2.7
```

### 场景 4：不小心把 node_modules 提交了

```bash
# 从 Git 移除（文件还在磁盘上）
git rm -r --cached node_modules/

# 确保 .gitignore 里有 node_modules/
# 然后重新提交
git commit -m "chore: 移除 node_modules"
```

### 场景 5：合并时有冲突

```bash
# 合并时出现冲突
git merge feature/xxx
# 提示 conflict

# 打开冲突文件，找到 <<<<<<< 和 >>>>>>> 标记
# 手动选择保留哪部分，删掉标记

# 解决后标记
git add 冲突文件
git commit -m "merge: 合并 feature/xxx"
```

## 五、一人公司的额外建议

### 1. 远程仓库选择
- **Gitee（码云）**：国内速度快，私有仓库免费，推荐
- **GitHub**：国际主流，但国内访问慢
- 两个都注册，互为备份也可以

### 2. 每日提交习惯
- 每天结束前 `git status` 看看有没有没提交的改动
- 改完一个功能就提交一次，不要攒一堆改动一起提交
- 提交信息写清楚改了什么，半年后自己还能看懂

### 3. 定期备份
- 远程仓库本身就是备份，确保每天 push
- 每月打包一份完整项目到网盘 / 移动硬盘（含 node_modules 的完整版）

### 4. 版本号规则
```
v1.2.8
│ │ │
│ │ └── 小修复（修 bug、改文案）
│ └──── 小功能（加新功能、UI 调整）
└────── 大版本（架构变动、重大更新）
```

### 5. 不确定就先备份
- 任何不确定的操作前，先 `git stash`（暂存改动）或 `git branch backup`（建个备份分支）
- 永远不用 `git push --force`（除非你 100% 确定后果）

## 六、最简工作流（背下来就够了）

```
每次改代码：
  1. git pull                              # 拉最新
  2. git checkout -b feature/改什么        # 切分支
  3. ... 改代码、测试 ...
  4. git add .                             # 暂存
  5. git commit -m "fix: 描述改了什么"       # 提交
  6. git checkout main                     # 切回 main
  7. git merge feature/改什么              # 合并
  8. git tag v1.2.8                        # 打标签（发布时）
  9. git push && git push origin v1.2.8    # 推送
  10. git branch -d feature/改什么          # 删分支
```

这 10 步就是全部。每次小迭代照着走，代码版本就不会乱。
